DESCRIPCION DEL FRONTEND WEB DE pseudoWeb

1. Proposito general

La aplicacion web de pseudoWeb es la capa visual del proyecto y funciona como un entorno de trabajo para escribir pseudocodigo, ejecutarlo, observar su salida y revisar errores. Su objetivo no es solamente mostrar un editor con un boton de ejecutar, sino actuar como un panel interactivo que conecta tres niveles del sistema: la interfaz de usuario, el flujo de ejecucion del interprete y la presentacion de resultados.

La app esta pensada como una experiencia tipo dashboard. El usuario entra a una pantalla principal con una barra superior, un menu lateral y un area central dinamica. Dependiendo de la vista elegida, el contenido principal cambia entre el editor, la consola de salida y el panel de errores.

2. Entrada de la aplicacion

El punto de arranque del frontend es el montaje de React en [src/main.tsx](src/main.tsx). Alli se renderiza [App](src/App.tsx) dentro de `React.StrictMode`, y se importa la hoja global de estilos [src/index.css](src/index.css).

La estructura de arranque es simple y deliberada: no hay un router de paginas ni un sistema de navegacion complejo. La experiencia se resuelve dentro de una sola pantalla, con cambios de vista controlados por estado local.

3. Arquitectura general

La arquitectura del web esta organizada por responsabilidades:

- [src/App.tsx](src/App.tsx) coordina el estado global de la UI.
- [src/hooks/useInterpreter.ts](src/hooks/useInterpreter.ts) encapsula el proceso de ejecutar pseudocodigo.
- [src/components/CodeEditor.tsx](src/components/CodeEditor.tsx) renderiza el editor de texto.
- [src/components/ConsolePanel.tsx](src/components/ConsolePanel.tsx) presenta salida, errores e interaccion de entrada.
- [src/components/SideNavBar.tsx](src/components/SideNavBar.tsx) controla el menu lateral y la navegacion entre vistas.
- [src/hooks/useCodeEditorKeyboard.ts](src/hooks/useCodeEditorKeyboard.ts) implementa atajos basicos de edicion.
- [src/constants/menuConfig.ts](src/constants/menuConfig.ts) define las opciones del menu.
- [src/types/ui.ts](src/types/ui.ts) centraliza los tipos de la capa de UI.

En la practica, `App` actua como orquestador. Mantiene el estado de pantalla y delega a los componentes especializados. Esa separacion evita que la logica de ejecucion se mezcle con la presentacion.

4. Estructura visual

La interfaz actual usa un layout de pantalla completa con tres regiones claras:

- Una barra superior fija con marca y acceso rapido al menu.
- Un panel lateral de navegacion con opciones de vista y accion de nuevo script.
- Un panel central que muestra una sola vista activa a la vez.

El contenedor principal usa un fondo con degradados suaves y la tarjeta central tiene bordes redondeados, sombra blanda y efecto de vidrio. La estetica es clara, tecnica y orientada a lectura de codigo.

El responsive behavior se resuelve con Tailwind:

- En escritorio, el sidebar puede contraerse o expandirse.
- En mobile, el sidebar se convierte en drawer flotante con overlay.
- El area central se adapta para conservar altura y scroll propio.

5. Flujo de navegacion de la UI

El estado de navegacion principal vive en `App` mediante `activeMenu`. Los valores posibles son `codigo`, `consola`, `errores` y `nuevoScript` segun [src/types/ui.ts](src/types/ui.ts), aunque en la vista actual `nuevoScript` funciona mas como accion que como pantalla independiente.

El flujo de cambio de vistas es este:

1. El usuario elige una opcion en el menu lateral.
2. `App` actualiza `activeMenu`.
3. El panel central muestra `CodeEditor` o `ConsolePanel` segun corresponda.
4. Si el usuario ejecuta codigo, la vista cambia automaticamente a `consola`.
5. Si ocurre un error de ejecucion, la vista se redirige a `errores`.

Ese cambio de pantalla no depende de una URL. Es una navegacion interna basada en estado, lo que mantiene el flujo rapido y evita recargas o transiciones innecesarias.

6. Editor de codigo

El editor esta implementado en [src/components/CodeEditor.tsx](src/components/CodeEditor.tsx). Es un `textarea` estilizado con numeracion de lineas sincronizada visualmente a la izquierda. El componente ofrece una experiencia simple pero funcional para escribir pseudocodigo.

Comportamientos relevantes del editor:

- Permite escribir y editar libremente el contenido.
- Muestra una cantidad dinamica de lineas segun el texto actual.
- Incluye botones para aumentar o reducir el tamaño de fuente.
- Deshabilita el boton de ejecutar cuando no hay codigo o cuando ya se esta ejecutando.
- Mantiene el scroll de la columna de numeros alineado con el scroll del textarea.

El teclado del editor se complementa con [src/hooks/useCodeEditorKeyboard.ts](src/hooks/useCodeEditorKeyboard.ts), que implementa dos ayudas importantes:

- `Tab` inserta o reduce indentacion de forma controlada.
- `Enter` preserva la indentacion de la linea actual al crear una nueva linea.

Esto hace que la escritura de pseudocodigo se sienta mas cercana a un editor especializado que a un textarea comun.

7. Consola y errores

La salida del interprete se muestra en [src/components/ConsolePanel.tsx](src/components/ConsolePanel.tsx). Este panel cumple varias funciones a la vez:

- Mostrar lineas de salida normal.
- Mostrar mensajes de error runtime cuando existen.
- Solicitar entrada adicional al usuario si la ejecucion lo requiere.
- Permitir limpiar la consola.
- Permitir reiniciar la ejecucion desde el mismo panel.

La consola mantiene auto-scroll hacia el final cuando llegan nuevas lineas o cuando aparece una solicitud de entrada. Si el interprete pide un valor, aparece un input enfocado automaticamente, listo para responder con Enter.

La vista de errores reutiliza el mismo panel, pero con un modo especifico para pintar el error runtime y sus metadatos. De esta forma, la app no duplica componentes y conserva una unica superficie de lectura para salida y diagnostico.

8. Flujo interno de ejecucion

La logica mas importante del frontend esta encapsulada en [src/hooks/useInterpreter.ts](src/hooks/useInterpreter.ts). Este hook hace de puente entre la UI y el motor de interpretacion de `@pseudoweb/core`.

El flujo interno de ejecucion es el siguiente:

1. El usuario pulsa ejecutar desde el editor.
2. `App` invoca `execute(code)`.
3. El hook limpia el estado previo, reinicia la salida y marca la ejecucion como activa.
4. Si el texto esta vacio, devuelve un resultado fallido con un mensaje explicito.
5. Si hay codigo, se crea un `Lexer`, se tokeniza, se crea un `Parser` y se parsean las sentencias.
6. Se instancia un `Evaluator` con un `Environment` nuevo y dos callbacks: uno para salida y otro para solicitar entrada.
7. El evaluador procesa el programa.
8. Al terminar, el hook guarda el resultado final con exito, variables y tiempo de ejecucion.
9. Si aparece un error, se normaliza a una estructura de error de UI con tipo, mensaje y, cuando existe, linea.
10. El estado de ejecucion se cierra y se limpia cualquier solicitud de input pendiente.

Este hook tambien contiene una pieza importante de interaccion: `submitInput`. Cuando el interprete espera un valor, el hook expone un mecanismo para resolver esa espera. El valor ingresado se parsea antes de enviarse al evaluator:

- Nulos o vacios se interpretan como `null`.
- Numeros enteros o decimales se convierten a `Number`.
- `true` y `false` se convierten a booleanos.
- Cadenas entre comillas simples o dobles se normalizan quitando las comillas.
- El resto se conserva como texto.

Eso permite que la consola acepte entrada flexible sin obligar al usuario a introducir siempre el mismo formato.

9. Manejo de estados de la UI

`App` concentra varios estados locales que controlan la experiencia completa:

- `activeMenu` define la vista visible.
- `isSidebarCollapsed` controla el sidebar en escritorio.
- `isMobileDrawerOpen` controla el drawer del menu en pantallas pequenas.
- `isConsoleCleared` recuerda si la consola fue limpiada manualmente.
- `consoleInput` guarda el texto que el usuario escribe en la consola.
- `code` contiene el pseudocodigo actual del editor.

Ademas, `App` observa el resultado de ejecucion. Si el resultado es un fallo, la interfaz se mueve automaticamente a la vista de errores. Eso evita que el usuario tenga que buscar manualmente el motivo de una falla luego de ejecutar.

10. Componentes reutilizables y piezas de extension

El paquete web incluye componentes que no siempre estan conectados en la ruta principal, pero que forman parte del lenguaje visual y de la futura expansion del producto:

- [src/components/TopNavBar.tsx](src/components/TopNavBar.tsx) propone una barra superior alternativa con acciones rapidas.
- [src/components/VariablesPanel.tsx](src/components/VariablesPanel.tsx) modela una tabla de variables en scope.
- [src/components/StatusBadge.tsx](src/components/StatusBadge.tsx) estandariza etiquetas de estado.
- [src/components/TypeBadge.tsx](src/components/TypeBadge.tsx) representa tipos de variables con colores.
- [src/components/MenuItem.tsx](src/components/MenuItem.tsx) encapsula la presentacion de cada entrada del sidebar.

Estos archivos muestran una intencion clara de escalar la experiencia hacia un dashboard mas rico, con inspeccion de variables, indicadores de estado y posiblemente historiales o paneles mas detallados.

11. Estilos y sistema visual

La hoja global [src/index.css](src/index.css) define la base tipografica y de foco. El proyecto usa `JetBrains Mono` para superficies tecnicas y `Manrope` para el texto general. El resultado busca un equilibrio entre legibilidad y caracter visual.

La UI se apoya en Tailwind para la composicion rapida de layouts y clases utilitarias. Ademas, existen estilos locales en [src/App.css](src/App.css) para una version alternativa del shell visual, con variables de color, paneles y tarjetas. Aunque el shell actual de [src/App.tsx](src/App.tsx) usa clases utilitarias directamente, ese archivo conserva una referencia de diseño y una base conceptual para ampliar o reestilizar la experiencia.

12. Relacion con el core

El frontend depende de `@pseudoweb/core`, que provee `Lexer`, `Parser`, `Evaluator` y `Environment`. La capa web no interpreta por si misma el lenguaje; solo traduce la interaccion del usuario a llamadas al core y luego presenta los resultados.

Eso separa claramente dos responsabilidades:

- El core decide la semantica del pseudocodigo.
- La web decide como se escribe, como se ejecuta y como se muestran los resultados.

13. Comportamiento de errores

La aplicacion diferencia entre tres situaciones principales:

- Sin codigo para ejecutar.
- Error de parseo o runtime durante la ejecucion.
- Ejecucion correcta con salida normal.

En caso de error, la UI no solo muestra un mensaje general. Tambien intenta conservar detalle util para depuracion, como tipo de error y ubicacion por linea cuando esta disponible. Si la consola fue limpiada manualmente, el panel de errores y salida reflejan ese estado para no confundir al usuario con resultados previos.

14. Experiencia de usuario

La experiencia esta orientada a flujo rapido:

- Escribir en el editor.
- Ejecutar con un boton visible y deshabilitado cuando no aplica.
- Leer la salida en una consola con auto-scroll.
- Responder inputs cuando el programa los solicita.
- Saltar automaticamente al panel de errores si algo falla.

Ese recorrido reduce friccion y hace que la app se comporte como una herramienta de practica y depuracion, no como un formulario estatico.

15. Resumen tecnico breve

En terminos practicos, la web de pseudoWeb es una SPA de React + TypeScript + Vite que organiza su funcionamiento alrededor de un editor, una consola y un menu lateral. El estado esta centralizado en `App`, la ejecucion depende de un hook especializado y la interfaz visual se construye con Tailwind y componentes pequenos reutilizables. La arquitectura es simple, modular y preparada para crecer hacia una vista mas completa de inspeccion y seguimiento.
