# REGLAS DEL LENGUAJE DE PSEUDOCÓDIGO

## 1. Estructura general de un algoritmo

Accion <nombre> : ES
    Ambiente
        // Declaraciones de constantes, variables. En este orden estrictamente si no hay constantes analiza las variables estas solo son globales. para declarar una constante se escribe su nombre que no debe ser palabra reservada del lenguaje
        <nombreConstante> = valor si es caracter o AN va con "" o '' ambos formatos son validos
        las variables se definen escribiendo su nombre que tampoco debe ser palabra reservada del lenguaje no deberia admitir caracteres especiales salvo "_" para reemplazar los espacios si se desea 
        <nombreVariable> : <tipo de dato> 
        // y declaraciones de funciones/procedimientos (opcional)
    Proceso
        // Instrucciones (asignaciones, condicionales, bucles, llamadas)
    FinAccion

Notas:
- El encabezado SIEMPRE empieza con "Accion", luego un nombre (ej. "nombre"), luego ":" y luego "ES".
- "ES" indica lenguaje español (por compatibilidad con otros idiomas).
- El bloque "Ambiente" es obligatorio.
- El bloque "Proceso" es obligatorio.
- Cada bloque termina con su respectivo "Fin..." (FinAccion, FinFuncion, etc.), exeptuando Ambiente y Proceso.
- Los saltos de línea son separadores de sentencias. o tambien podemos ejecutar mas de una sentencia en una misma linea separando sentencias con ";"

## 3. Funciones y procedimientos

Declaración dentro de Ambiente:
    Funcion <nombre>(parametros) : <tipo_retorno>
        Ambiente (opcional)
            // variables locales
        Proceso
            // instrucciones
            <nombre> := <expresion>
    FinFuncion

    Procedimiento <nombre>(parametros) // puedo tener procedimientos sin parametros 
        Ambiente (opcional)
            // variables locales
        Proceso
    FinProcedimiento

Los parámetros pueden ser por valor o por referencia (preceder con "&").

## 4. Instrucciones principales

Asignación:
    <variable> := <expresion>

Condicionales:
    Si <condicion> Entonces
        ...
    SiNo 
        Si <condicion> Entonces
        ...
        FinSi
    SiNo
        ...
    FinSi

Bucles:
    Mientras <condicion> Hacer
        ...
    FinMientras

    Repetir
        ...
    HastaQue <condicion>

    Para <var> := <inicio> Hasta <fin> [Con Paso <paso>] Hacer
        ...
    FinPara

Lectura/Escritura:
    Leer(<variable>)
    Escribir(<expresión o cadena>) // si dentro del parentesis tengo '' o "" indica que es una cadena de texto para concatenar uso "," si no lleva comillas el sistema debe detectar que es una variable o constante debe controlar su existencia en el Ambiente sino lanzar error 

## 5. Orden estricto exigido

El analizador debe respetar el siguiente orden dentro de un bloque Ambiente:
1. Constantes
2. Tipos definidos por el usuario 
3. Variables globales
4. Declaraciones de funciones y procedimientos (pueden aparecer luego de las variables)

Si una función/procedimiento incluye su propio bloque Ambiente, internamente respeta el mismo orden.(las variables locales no deben llamarse igual que las globales los parametros no deben llamarse igual que los argumentos todo esto debe lansar errores)

## 6. Manejo de errores esperado

- Error léxico: carácter no reconocido (mostrar línea, columna).
- Error sintáctico: estructura incorrecta (ej. falta "ES" después del nombre).
- Error semántico: variable no declarada, tipo incompatible, etc.
- Error en tiempo de ejecución: división por cero, acceso a índice fuera de rango.

11) ❌ INCUMPLIMIENTOS REALES DEL PROGRAMA (ANÁLISIS 2026-05-06)

CRÍTICO - Discrepancias severas entre lo que AFIRMA este documento y lo que IMPLEMENTA el código:

11.1 FASE 4 SUBRUTINAS - DECLARADA "COMPLETADA" PERO NO FUNCIONA

✗ Llamadas a funciones en expresiones NO FUNCIONAN
  - Se declara: "Implementado"
  - Realidad: El parser NO parsea llamadas a funciones en parsePrimary()
  - Impacto: resultado := suma(1, 2) causa ParserError
  - Estado: FunctionCallNode existe pero NUNCA se genera
  - Evaluator: No tiene handler para FunctionCall (línea 50: "omitimos")

✗ Llamadas a procedimientos como sentencia NO FUNCIONAN
  - Se declara: "Implementado"
  - Realidad: No hay soporte sintáctico ni semántico
  - Impacto: mostrar(valor) es rechazado

✗ Scope local por invocación NO EXISTE
  - Se declara: "Implementado" 
  - Realidad: Environment puede anidarse pero nunca se crea scope para subrutinas
  - Impacto: Las funciones/procedimientos jamás se ejecutan

✗ Retorno por asignación al nombre de la función NO EXISTE
  - Se declara: "Implementado"
  - Realidad: No hay ReturnNode en AST, la palabra Retornar está en TokenType pero no se procesa
  - Impacto: Las funciones no pueden retornar valores

11.2 FASE 5 TIPOS Y BUILTINS - PARCIALMENTE INCOMPLETO

✗ AN(n) - Validación incompleta
  - Se declara: "Implementado en declaraciones, parametros y retorno"
  - Realidad: Se parsea pero el evaluator no valida longitud contra n
  - Impacto: Escribir(texto: AN(5)) acepta strings mayores a 5 caracteres

✗ REDOND(x) - NO ES UN BUILTIN FUNCIONAL
  - Se declara: "Implementado como función integrada"
  - Realidad: No existe en el parser ni evaluator
  - Impacto: REDOND(3.7) causa ParserError/RuntimeError
  - Verificable: No hay test que la use

✗ Compatibilidad de tipos en Segun - Sin validación estricta
  - Se declara: "Implementado"
  - Realidad: El evaluator acepta cualquier tipo sin validación
  - Impacto: Segun (logico) ... 1: Escribir() (caso entero) - se acepta erróneamente

11.3 FASE 3 SEMANTICA BASE - VALIDACIONES INCOMPLETAS

✗ Variables implícitas - PARCIALMENTE PERMITIDAS
  - Se declara: "Prohibir variables implicitas: Implementado"
  - Realidad: Existe código en evaluateAssignment que CREA variables si no existen
  - Impacto: x := 5 (sin declarar x) se acepta si la variable es nueva
  - Verificable: Línea del evaluator que crea variable dinámicamente

✗ Inmutabilidad real de constantes - NO SE VALIDA EN ASIGNACIÓN
  - Se declara: "Implementado"
  - Realidad: Falta detector de "intento de reasignar constante"
  - Impacto: c := 5; c := 10 es aceptado sin error

✗ Validación estricta de tipos en operaciones - PARCIAL
  - Se declara: "Implementado"
  - Realidad: concatenación implícita de strings en + (línea evaluator)
  - Impacto: "5" + 3 devuelve "53" en lugar de RuntimeError
  
✗ Validación de null en operaciones/condiciones - PARCIAL
  - Se declara: "Implementado"
  - Realidad: null en comparaciones devuelve false silenciosamente en lugar de RuntimeError
  - Impacto: (null < 5) no lanza error

11.4 FASE 1 CAMBIOS LEXICOS - "Remover Retornar" CONTRADICHO

✗ Retornar removido pero aparece en TokenType
  - Se declara en resumen: "Remover Retornar: Implementado"
  - Realidad: RETORNO aparece en tokenTypes.ts como palabra reservada
  - Impacto: Discrepancia entre afirmación y implementación

11.5 GAPS NO MENCIONADOS EN FASES PERO REQUERIDOS POR ESPECIFICACIÓN

✗ Parámetros por referencia (&)
  - ParameterNode tiene byReference: boolean pero NUNCA se usa
