Alineación con arquitectura de parser e interpreter
================================================================================


1. OBJETIVO
--------------------------------------------------------------------------------

Reorganizar la carpeta lexer/ para que siga los mismos patrones arquitectónicos
que parser/ e interpreter/: separación en orchestrator/, types/, constants/,
y capas con index.ts como re-exportadores centralizados.

El comportamiento del lexer no cambia. Solo cambia la organización,
la ubicación de los archivos y el tipado formal del contrato entre
el lexer y sus scanners especializados.

3. DIAGNÓSTICO — BRECHAS ACTUALES
--------------------------------------------------------------------------------

A continuación se listan los patrones que parser e interpreter aplican
y que el lexer actual no respeta.

  [1] Ausencia de capa orchestrator/
      El archivo lexer.ts vive suelto en la raíz.
      Parser e interpreter encapsulan su clase principal dentro de orchestrator/
      con separación entre fachada, estado interno y dispatcher.

  [2] Ausencia de capa types/
      Token, TokenType y tokenRules viven dispersos en la raíz.
      Parser define types/ con 8 archivos semánticos.
      Interpreter define types/ con interfaces de contexto.
      El lexer necesita lo mismo.

  [3] Ausencia de constants/errorMessages.ts
      Parser e interpreter centralizan todos sus errores en ese archivo.
      El lexer no tiene equivalente; los errores quedan dispersos o ausentes
      en los scanners.

  [4] Ausencia de interfaz formal LexerContext / ScannerContext
      Los scanners reciben un objeto state anónimo sin contrato tipado.
      Parser define ParserContext. Interpreter define EvaluatorContext.
      El lexer necesita ScannerContext como interfaz explícita para
      desacoplar los scanners del estado concreto y permitir tests aislados.

  [5] Ausencia de index.ts en subcarpetas
      scanners/ y utils/ no tienen index.ts.
      Todos los módulos de parser e interpreter usan index.ts como
      re-exportadores centralizados en cada subcarpeta.


4. PLAN DE ACCIÓN — PASO A PASO
--------------------------------------------------------------------------------

PASO 1 — Crear carpeta types/ y mover tipos existentes
  
  1.1  Crear types/tokenType.ts
       Mover el enum TokenType completo desde tokenTypes.ts (raíz).
       Sin cambios de contenido.

  1.2  Crear types/tokenRules.ts
       Mover KEYWORDS, isKeyword() y getKeywordType() desde tokenRules.ts (raíz).
       Sin cambios de contenido.

  1.3  Crear types/token.ts
       Extraer la interfaz Token desde lexer.ts (donde hoy es un export suelto).
       Contenido:

         export interface Token {
           type: TokenType
           lexeme: string
           literal: string | number | boolean | null
           line: number
           column: number
         }

  1.4  Crear types/lexerError.ts
       Definir la clase LexerError (análoga a ParserError en parser/
       y RuntimeError en interpreter/).
       Contenido:

         export class LexerError extends Error {
           constructor(
             message: string,
             public readonly line: number,
             public readonly column: number,
           ) {
             super(message)
             this.name = 'LexerError'
           }
         }

  1.5  Crear types/scannerContext.ts
       Re-exportar LexerContext como alias ScannerContext para que los scanners
       no importen desde orchestrator/ directamente (evita dependencia circular).
       Contenido:

         export type { LexerContext as ScannerContext } from '../orchestrator/lexerContext'

  1.6  Crear types/index.ts
       Re-exportar Token, TokenType, tokenRules, LexerError, ScannerContext.


PASO 2 — Crear carpeta orchestrator/

  2.1  Crear orchestrator/lexerContext.ts
       Definir la interfaz LexerContext: contrato formal que los scanners
       necesitan del estado del lexer. Reemplaza el objeto state anónimo.
       Contenido:

         export interface LexerContext {
           readonly line: number
           readonly column: number
           peek(): string
           peekNext(): string
           advance(): string
           isAtEnd(): boolean
           addToken(
             type: TokenType,
             lexeme: string,
             literal: Token['literal'],
             line?: number,
             column?: number,
           ): void
           sliceLexeme(start: number): string
         }

  2.2  Crear orchestrator/lexerState.ts
       Mover la lógica de estado de lexer.ts a LexerStateImpl, que implementa
       LexerContext. Mantiene source, start, current, line, column, tokens[].
       Implementa peek(), peekNext(), advance(), isAtEnd(), addToken(), sliceLexeme().
       Análogo a ParserStateImpl en parser/state/parserState.ts.

  2.3  Mover lexer.ts → orchestrator/lexer.ts
       La clase Lexer queda como fachada minimal:
         - Recibe source: string en el constructor.
         - Crea una instancia de LexerStateImpl.
         - Expone tokenize(): Token[] que delega a LexerStateImpl.
       Análogo a la clase Parser en parser/orchestrator/parser.ts.

  2.4  Crear orchestrator/index.ts
       Re-exportar Lexer y LexerContext.


PASO 3 — Crear carpeta constants/

  3.1  Crear constants/errorMessages.ts
       Centralizar todos los mensajes de error del lexer.
       Sigue el patrón exacto de parser/constants/errorMessages.ts
       e interpreter/constants/errorMessages.ts.
       Mensajes mínimos requeridos:

         export const ERR_UNTERMINATED_STRING = (line: number, col: number) =>
           `Cadena sin cerrar en línea ${line}, columna ${col}`

         export const ERR_UNEXPECTED_CHARACTER = (char: string, line: number, col: number) =>

         export const ERR_UNTERMINATED_BLOCK_COMMENT = (line: number, col: number) =>

  3.2  Crear constants/index.ts
       Re-exportar todos los mensajes.


PASO 4 — Actualizar carpeta scanners/

  4.1  Actualizar cada scanner para tipar el parámetro state como ScannerContext

  4.2  Actualizar cada scanner para importar mensajes de error

  4.3  Crear scanners/index.ts

9. NOTAS DE DISEÑO
--------------------------------------------------------------------------------

  - LexerStateImpl se ubica en orchestrator/ y no en una carpeta state/ separada
    porque el lexer no tiene la complejidad de fases que tiene el parser
    (ambiente → proceso → callables). Si en el futuro crece, se puede extraer
    a state/ sin afectar ningún consumidor externo.

  - ScannerContext en types/ es un alias de LexerContext en orchestrator/.
    Esto rompe la dependencia directa de scanners/ hacia orchestrator/,
    manteniendo el grafo de dependencias acíclico:
      orchestrator/ → types/ → (nada interno)
      scanners/     → types/ → (nada interno)

  - LexerError sigue el patrón de ParserError (parser) y RuntimeError (interpreter):
    clase que extiende Error con propiedades line y column para diagnósticos precisos.

  - El comportamiento de tokenize() es idéntico al actual. No hay cambios
    en la lógica de scanning, precedencia de caracteres ni generación de tokens.
