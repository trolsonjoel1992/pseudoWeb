  - Resumen funcional del estado del lexer en el repo:
    - El lexer es un escáner clásico por caracteres con un `LexerState` que mantiene posición, línea y columna, y produce una lista de `Token`.
    - Flujo principal (`Lexer.tokenize` / `scanToken`):
      1. Ignora espacios en blanco y tabs.
      2. Emite `SaltoDeLinea` para `\n`.
      3. Omite comentarios de bloque `/* ... */` y comentarios de línea `// ...`.
      4. Si detecta comillas dobles o simples, consume una cadena con `scanStringToken` (soporta escapes y distingue `Alfanumerico` vs `Caracter`).
      5. Si detecta dígito, consume número con `scanNumberToken` (detecta `Entero` vs `Real` y guarda `literal` numérico).
      6. Si detecta letra, consume identificador con `scanIdentifierToken` y resuelve si es palabra reservada consultando `KEYWORDS` (mapa `lexeme.toLowerCase()` → `TokenType`).
      7. Para cualquier otro caracter relevante, usa `scanOperatorToken` que reconoce operadores y puntuación (`:=`, `+`, `-`, `*`, `**`, `/`, `=`, `<`, `>`, `<=`, `>=`, `<>`, `(`, `)`, `,`, `;`, `..`, `:`).

    - Palabras clave / tokens soportados (no exhaustivo): `Accion`, `FinAccion`, `Si`, `SiNo`, `FinSi`, `Mientras`, `FinMientras`, `Para`, `FinPara`, `Repetir`, `Hasta`, `HastaQue`, `Segun`, `FinSegun`, `Leer`, `Escribir`, `Funcion`, `Procedimiento`, `Verdadero`, `Falso`, `Entero`, `Real`, `Caracter`, `Alfanumerico`, `Logico`, ... etc. (ver `tokenType.ts`).

    - Resolución de identificadores: `scanIdentifierToken` llama a `resolveIdentifierType(lexeme)` que convierte `lexeme.toLowerCase()` y busca en `KEYWORDS`. Caso especial: si el lexema exacto es `DIV` o `MOD` (mayúsculas), `resolveIdentifierType` devuelve `TokenType.Div` o `TokenType.Mod`.

    - Literales: `Verdadero`/`Falso` se mappean a token booleano con `literal: true/false`. Los números agregan `literal` numérico. Las strings usan `literal` con el valor interpretado (escapes resueltos).

  - Observaciones específicas respecto a la integración de `Secuencia`:
    - No se añadió ninguna nueva palabra reservada al lexer. La sintaxis `Secuencia de` se reconoce en el parser comprobando `state.check(TokenType.Identificador)` y comparando `state.peek().lexeme.toLowerCase() === 'secuencia'`.
    - Dado que `secuencia` no está listada en `KEYWORDS`, el lexer emite `TokenType.Identificador` para la palabra `Secuencia` y el parser la interpreta según esa lexema. Esto es funcional y deliberado (permitir palabras como `secuencia` case-insensitive sin cambiar la tabla de keywords).
    - La palabra `de` también se consume como identificador opcional por `parseDataType` (no es necesaria como token reservado).
    - Las aliases `FDS`/`NFDS` no fueron añadidas como tokens; el parser normaliza el nombre de la llamada desde el identificador recibido y lo mapea internamente a `FinDeSecuencia`/`NoFinDeSecuencia`.

5) Cómo funciona el `Avanzar` (implementación en este repo)

  - Formas soportadas:
    1. Procedural: `Avanzar(secuencia, ventana)` — asigna el siguiente elemento a `ventana` en el entorno y avanza `position`.
    2. Funcional: `valor := Avanzar(secuencia)` — builtin `Avanzar` devuelve el siguiente elemento y avanza `position`.

  - Precondiciones comunes:
    - `secuencia` debe ser un `SequenceValue` (runtime).
    - `secuencia.mode === 'read'` (usar `Arrancar(secuencia)` previamente).
    - `secuencia.mode !== 'closed'`.
    - `secuencia.position < secuencia.elements.length` (sino se lanza error `FinDeSecuencia` / `SequenceEndReached`).

  - Efectos:
    - Obtiene `element = secuencia.elements[secuencia.position]`.
    - Valida `element` contra `secuencia.elementType` (si no coincide: `SequenceTypeMismatchError`).
    - Procedural: asigna a variable `ventana` y hace `secuencia.position++`.
    - Funcional: retorna `element` y hace `secuencia.position++`.

Explicación del funcionamiento del lexer (apéndice)

  El lexer del proyecto sigue un diseño determinista por caracteres con componentes especializados para cada tipo de token:

  - Estado: `LexerState` mantiene `source`, `start`, `current`, `line`, `column` y una lista de tokens.
  - Orquestador (`Lexer.scanToken`): lee el caracter actual y determina qué escáner invocar:
    * Espacios y tabs: se consumen y se ignoran.
    * Saltos de línea: se consumen y emiten `SaltoDeLinea`.
    * Comentarios: `/* ... */` y `// ...` se saltan usando funciones dedicadas.
    * Strings: `"..."` y `'...'` son consumidas por `scanStringToken`, que soporta escapes (`\\n`, `\\t`, `\\r`, `\\"`, `\\\\`, etc.). Strings dobles generan token `Alfanumerico` y comillas simples generan `Caracter`.
    * Números: `scanNumberToken` reconoce enteros y reales ('.' decimal), y guarda el literal numérico.
    * Identificadores / Palabras reservadas: `scanIdentifierToken` consume una secuencia alfanumérica y llama `resolveIdentifierType(lexeme)` que usa un mapa `KEYWORDS` en minúsculas para detectar keywords y asignar el `TokenType` apropiado; caso especial `DIV` y `MOD` son mapeados a tokens de operador.
    * Operadores y puntuación: `scanOperatorToken` reconoce pares/multicaracter (`:=`, `**`, `..`, `<=`, `>=`, `<>`) y tokens simples.

  - Emisión: cada escáner llama a `context.addToken(type, lexeme, literal, line, column)` para registrar el token con su lexema y, cuando procede, un `literal` (valor numérico, booleano o contenido de string).

  - Case insensitivity: las palabras clave se resuelven con `lexeme.toLowerCase()` en `KEYWORDS`, por lo que el lenguaje es insensible a mayúsculas/minúsculas para keywords.

  - Robustez: el lexer lanza `LexerError` con códigos `ErrorCode.LEX_*` en casos de carácter inesperado o string no terminado.

Fin del informe.
