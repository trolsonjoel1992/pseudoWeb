── DIAGNÓSTICO PREVIO ──────────────────────────────────────────────────────────

Antes de proponer cualquier movimiento estructural, se identifican tres categorías
de problemas con diferente nivel de urgencia:

CRÍTICOS (bloquean extensibilidad):
  - evaluator.ts mezcla orquestación, despacho, invocación de callables y lógica
    de builtin (REDOND) en un único archivo. Cualquier nueva builtin o sentencia
    amplía un archivo que ya es demasiado grande.
  - No existe un mecanismo formal de registro de builtins; REDOND es un caso
    especial ad-hoc embebido en la lógica central.

MODERADOS (aumentan el costo de mantenimiento):
  - La carpeta interpreter/ es plana. Los dominios (callables, environment,
    context, evaluators) coexisten sin separación física, dificultando la
    navegación y el razonamiento sobre límites de responsabilidad.
  - No hay barrel exports (index.ts) por dominio, lo que hace que los imports
    sean frágiles ante reestructuraciones.

DIFERIDOS (válidos pero riesgosos si se hacen ahora):
  - typeSystem.ts concentra validación, coerción y reglas específicas de sentencias.
    Tocarlo mientras se mueve estructura aumenta la superficie de error innecesariamente.
  - Partir controlFlowEvaluator.ts en archivos por sentencia (If, While, For)
    agrega granularidad pero no resuelve ningún problema concreto hoy.


── PRINCIPIOS QUE GUÍAN ESTE PLAN ──────────────────────────────────────────────

1. Un solo tipo de cambio por fase: o estructura, o comportamiento. Nunca ambos.
2. El árbol de tests debe pasar al 100% después de cada fase antes de continuar.
3. Los textos de error (substrings) son contrato público; no se modifican.
4. typeSystem.ts no se toca en la Fase 1 ni en la Fase 2.
5. Cada movimiento de archivo se acompaña de su barrel export y la actualización
   de todos sus importadores en el mismo commit.
6. evaluator.ts debe quedar como orquestador puro: sin lógica de dominio.

── DIAGNÓSTICO PUNTUAL DE evaluator.ts ACTUAL ──────────────────────────────────

Problema 1 — Wrappers privados sin lógica (ruido puro):
  Los siguientes métodos son intermediarios de una sola línea que no aportan
  abstracción ni lógica propia:

    evaluateWrite(node)    → evaluateWriteNode(node, this.context)
    evaluateRead(node)     → evaluateReadNode(node, this.context)
    evaluateIf(node)       → evaluateIfNode(node, this.context)
    evaluateWhile(node)    → evaluateWhileNode(node, this.context)
    evaluateFor(node)      → evaluateForNode(node, this.context)
    evaluateSwitch(node)   → evaluateSwitchNode(node, this.context)
    evaluateDoWhile(node)  → evaluateDoWhileNode(node, this.context)

  Estos 7 métodos suman ~21 líneas que se eliminan completamente.

Problema 2 — evaluateStatement mezcla responsabilidades con el evaluador:
  El switch de 10 casos vive dentro de la clase Evaluator, que ya se encarga
  de construcción, cableado de dependencias y ciclo principal de ejecución.
  Son dos responsabilidades distintas en la misma clase.

Problema 3 — evaluateBlock duplica trabajo del dispatcher:
  evaluateBlock llama a evaluateStatement en un loop. Si el dispatcher
  encapsula evaluateStatement, evaluateBlock también puede vivir ahí.

── ESTRUCTURA OBJETIVO ─────────────────────────────────────────────────────────

orchestrator/
├── evaluator.ts
│     Responsabilidad única: construcción + ciclo principal
│     Contiene:
│       - constructor (inicialización de dependencias)
│       - evaluate() — registra ambiente y llama al dispatcher
│       - initializeEnvironmentDeclarations()
│       - evaluateExpression() — se queda acá porque la usan callables
│       - invokeFunction() y invokeProcedure()
│       - evaluateAssignment() y evaluateCallStatement()
│         (se quedan porque acceden directamente a this.environment,
│          this.registry y this.builtinRegistry — no son wrappers vacíos)
│
└── statementDispatcher.ts
      Responsabilidad única: despacho de sentencias al evaluador correcto
      Contiene:
        - clase StatementDispatcher
        - dispatch(node: StatementNode): Promise<void>  ← el switch
        - dispatchBlock(nodes: StatementNode[]): Promise<void>  ← el loop
        - Llamadas directas a los evaluadores especializados (sin wrappers)

── FASE 1: CREAR statementDispatcher.ts ────────────────────────────────────────

1.1 Crear el archivo orchestrator/statementDispatcher.ts

    Firma de la clase:

      export class StatementDispatcher {
        constructor(private readonly context: EvaluatorContext) {}

        async dispatch(node: StatementNode): Promise<void> { ... }
        async dispatchBlock(nodes: StatementNode[]): Promise<void> { ... }
      }

    El constructor recibe únicamente EvaluatorContext porque todos los
    evaluadores especializados ya lo reciben como única dependencia.

    El switch dentro de dispatch() llama directo, sin métodos intermedios:

      case 'Write':
        await evaluateWriteNode(node as WriteNode, this.context)
        return
      case 'If':
        await evaluateIfNode(node as IfNode, this.context)
        return
      // etc.

    Los casos 'VariableDeclaration', 'Assignment' y 'CallStatement' NO van
    al dispatcher porque necesitan acceso a environment, registry y
    builtinRegistry directamente — quedan en el evaluador.

    Alternativa para esos tres casos: el dispatcher los delega a callbacks
    inyectados en el constructor. Ver nota al final de este plan.

1.2 Ejecutar: tsc --noEmit
    El archivo nuevo no debe introducir errores de tipos antes de integrarse.

── FASE 2: INTEGRAR EN evaluator.ts ────────────────────────────────────────────

2.1 Instanciar StatementDispatcher en el constructor de Evaluator:

      this.dispatcher = new StatementDispatcher(this.context)

2.2 Reemplazar el método evaluateStatement por delegación al dispatcher:

      private async evaluateStatement(node: StatementNode): Promise<void> {
        // Casos con acceso directo a dependencias internas
        switch (node.type) {
          case 'VariableDeclaration':
            this.evaluateVariableDeclaration(node as VariableDeclarationNode)
            return
          case 'Assignment':
            await this.evaluateAssignment(node as AssignmentNode)
            return
          case 'CallStatement':
            await this.evaluateCallStatement(node as CallStatementNode)
            return
        }
        // Todo lo demás al dispatcher
        await this.dispatcher.dispatch(node)
      }

2.3 Reemplazar evaluateBlock por delegación al dispatcher:

      private async evaluateBlock(statements: StatementNode[]): Promise<void> {
        await this.dispatcher.dispatchBlock(statements)
      }

    ATENCIÓN: dispatchBlock necesita poder llamar a evaluateStatement para
    los tres casos especiales. Dos opciones:

    Opción 2a (simple): dispatchBlock llama a dispatch() internamente y el
    evaluador mantiene su propio loop para los casos especiales. En la práctica
    evaluateBlock queda igual que hoy pero delegando al dispatcher para el resto.

    Opción 2b (limpia): inyectar un callback evaluateStatement en el dispatcher
    para que dispatchBlock pueda manejar todos los casos uniformemente:

      this.dispatcher = new StatementDispatcher(
        this.context,
        (node) => this.evaluateStatement(node)   // callback
      )

    RECOMENDACIÓN: Opción 2b. Evita que el evaluador tenga dos rutas de
    despacho distintas y permite que dispatchBlock sea el único punto de
    entrada para ejecutar bloques de sentencias.

2.4 Eliminar los 7 métodos privados wrapper (evaluateWrite, evaluateRead,
    evaluateIf, evaluateWhile, evaluateFor, evaluateSwitch, evaluateDoWhile).

PLAN DE REFACTORIZACIÓN — EXTRACCIÓN DE CallableInvoker

── OBJETIVO ────────────────────────────────────────────────────────────────────

Extraer la lógica de resolución e invocación de callables de evaluator.ts
hacia un módulo que pertenece semánticamente al dominio callables/.

La razón NO es reducir líneas. Es que evaluator.ts actualmente conoce:
  - Que los builtins tienen prioridad sobre las funciones de usuario
  - Que si pedís una función y existe un procedimiento con ese nombre, el
    error es específico (y viceversa)
  - Que la búsqueda sigue el orden: builtinRegistry → callableRegistry

Esa lógica de resolución de nombres es dominio de callables/, no del orquestador.

Resultado estructural esperado:

  callables/
  ├── callableExecutor.ts     (sin cambios)
  ├── callableRegistry.ts     (sin cambios)
  ├── callableInvoker.ts      ← nuevo
  └── index.ts                (actualizado)

  orchestrator/
  └── evaluator.ts            (~130 líneas — sin lógica de resolución de nombres)

── ANÁLISIS DE LO QUE SE EXTRAE ────────────────────────────────────────────────

Los dos métodos que salen de evaluator.ts:

  invokeFunction(name, args):
    1. Busca en builtinRegistry → ejecuta si existe
    2. Busca en callableRegistry → lanza error específico si es procedimiento
    3. Ejecuta con callableExecutor.executeFunction()

  invokeProcedure(name, args):
    1. Busca en callableRegistry → lanza error específico si es función
    2. Ejecuta con callableExecutor.executeProcedure()

Dependencias que necesita CallableInvoker:
  - BuiltinRegistry         (resolución de builtins)
  - CallableRegistry        (resolución de funciones/procedimientos de usuario)
  - CallableExecutor        (ejecución real)

Las tres ya existen en callables/ o en builtins/. No se crea nada nuevo,
solo se reagrupa la lógica donde corresponde.

── FASE 1: CREAR callableInvoker.ts ────────────────────────────────────────────

1.1 Crear packages/core/src/interpreter/callables/callableInvoker.ts

    Firma de la clase:

      export class CallableInvoker {
        constructor(
          private readonly builtinRegistry: BuiltinRegistry,

          private readonly executor: CallableExecutor,
        ) {}

        async invokeFunction(name: string, args: unknown[]): Promise<unknown>
        async invokeProcedure(name: string, args: unknown[]): Promise<void>
      }

    El cuerpo de cada método es una copia exacta del método homónimo en
    evaluator.ts — sin cambios de lógica, sin cambios de mensajes de error.

    CRÍTICO: Los mensajes de error no se modifican. Son contrato público:
      - `'${name}' es un procedimiento y no puede usarse dentro de una expresión.`
      - `No existe una función llamada '${name}'.`
      - `'${name}' es una función y debe usarse dentro de una expresión.`
      - `No existe un procedimiento llamado '${name}'.`

1.2 Ejecutar: tsc --noEmit
    El archivo nuevo debe compilar sin errores antes de integrarse.

── FASE 3: INTEGRAR EN evaluator.ts ────────────────────────────────────────────

3.2 Instanciar en el constructor, después de que callableExecutor esté creado:

    ATENCIÓN: CallableExecutor se construye antes en el constructor porque

3.3 Actualizar el context que se pasa a ContextFactory:

3.4 Actualizar evaluateCallStatement para usar el invoker:

    Antes:
      if (this.registry.isProcedure(node.call.name)) {
        await this.invokeProcedure(node.call.name, args)
        return
      }
      if (this.registry.isFunction(node.call.name)) {
        await this.invokeFunction(node.call.name, args)
        return

      throw new RuntimeError(`No existe una función o procedimiento llamado '${node.call.name}'.`)

    Después:
      if (this.registry.isProcedure(node.call.name)) {
        await this.invoker.invokeProcedure(node.call.name, args)
        return
      }
      if (this.registry.isFunction(node.call.name)) {
        await this.invoker.invokeFunction(node.call.name, args)
        return
